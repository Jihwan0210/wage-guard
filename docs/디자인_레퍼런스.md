# wageback 디자인 레퍼런스

공공·금융·노무·외국인 대상 서비스의 공개 문서와 화면 설명을 직접 찾아보고, 우리 화면에 가져올 것과 피할 것을 정리했다.
페이지에서 확인한 내용만 적었다. 추정은 '(추정)', 열지 못한 곳은 '직접 확인 못 함'으로 표시했다.

## 요약: 우리 화면에 바로 적용할 규칙 12개

1. **한 화면에 질문 하나만 둔다. 질문 문장이 곧 화면 제목(h1)이자 입력칸 label이다.** 화면마다 제목을 다르게 쓴다. (1, 4, 13)
2. **다음으로 가는 주 버튼은 한 화면에 하나다.** 화면을 열자마자 보여야 한다. 문구는 '다음'보다 눌렀을 때 일어나는 일을 말한다. 예: '계속', '결과 보기', '진정서 만들기'. (1, 13, 14)
3. **모든 질문 화면 맨 위에 '이전' 링크를 둔다.** 브라우저 뒤로가기도 직전 화면을 그대로 돌려줘야 한다. (1)
4. **힌트는 짧은 한 문장으로 쓰고 마침표와 링크를 넣지 않는다.** 긴 설명은 접힌 '자세히'에 넣는다. 본문은 50단어 아래로 줄인다. (1, 3, 4)
5. **'모르겠어요'를 정식 선택지로 둔다.** 필수 칸에 * 표시를 하지 않는다. 안 받아도 되는 칸에만 '(선택)'이라고 쓴다. (1)
6. **금액·시간 칸은 `inputmode="numeric"`을 쓰고 `type="number"`는 쓰지 않는다.** '원'은 칸 밖에 붙이고 label에도 '(원)'을 적는다. 사용자가 '원'이나 쉼표를 같이 입력해도 오류로 처리하지 않는다. (3, 5)
7. **오류는 두 곳에 같은 문장으로 보여준다.** 화면 위쪽 요약과 해당 칸 바로 옆이다. 문장은 '시급을 입력하세요', '하루 일한 시간은 24 이하로 입력하세요'처럼 고칠 방법을 말한다. 경고문을 미리 깔아 두지 않는다. (3, 13)
8. **확인 화면은 '항목 | 읽은 값 | 바꾸기' 목록으로 만든다.** 바꾸고 나면 확인 화면으로 바로 돌아온다. 제출 버튼 위에는 '맞으면 계산합니다'처럼 이 단계의 의미를 한 줄 적는다. (2, 4)
9. **결과 화면에서는 금액 한 덩어리만 크게 보여준다.** 바로 아래에 그 금액의 뜻과 다음 행동을 짧게 적는다. 결과 강조 상자는 결과 화면에서만 쓴다. 계산이 틀릴 수 있다는 안내와 노동청 연락처를 함께 둔다. (6, 7, 8, 13)
10. **진행 표시는 일단 넣지 않고 시험해 본다.** 필요하면 '질문 3/6' 같은 글자로만 넣는다. 질문 수가 답에 따라 달라지면 단계 막대를 쓰지 않는다. (1, 5)
11. **노랑은 포커스 표시와 배경 강조에만 쓴다.** 노랑 위 글씨는 먹색(#0b0c0c 계열)으로 쓴다. 노랑을 흰 바탕 위 글씨나 얇은 선 색으로 쓰지 않는다(추정: 대비 부족). 본문은 16px 아래로 내리지 않는다. (9)
12. **문장은 짧은 한 생각으로 쓰고 관용구·비유는 쓰지 않는다.** 외국인 사용자가 번역기를 돌려도 뜻이 남게 하려는 것이다. 언어 선택에는 언어 이름을 그 언어로 쓰고(English, Tiếng Việt), `lang` 속성을 붙인다. (5, 10, 11, 15)
13. **서류 촬영 화면은 테두리 안내, 자동 선택, 즉시 재촬영 순서로 만든다.** 화면에 서류를 맞출 테두리를 보여준다. 여러 장면 중 잘 읽히는 장면을 고른다. 빛 반사·흐림·잘림이 있으면 바로 다시 찍게 한다. 실패 문장은 이유별로 따로 쓴다. (3, 12, 19)

## 서비스별 관찰

### 1. GOV.UK Design System: 질문 페이지 패턴
- 주소: https://design-system.service.gov.uk/patterns/question-pages/
- 가져올 것:
  - **입력 흐름:** 'One thing per page'. 처음에는 한 페이지에 질문 하나로 시작한다. 이미 받은 정보는 다시 묻지 않는다.
  - **입력 흐름:** `<label>`이나 `<legend>`를 그대로 페이지 제목으로 쓴다. 화면 읽기 사용자가 같은 말을 두 번 듣지 않게 하려는 것이다. 제목은 현재 질문에 맞춰 쓰고, 큰 단계 이름은 제목 위 작은 캡션으로 둔다(예: "About you").
  - **입력 흐름:** 버튼 문구는 "Next"가 아닌 "Continue"이고 **왼쪽 정렬**한다. 사용자가 놓치지 않게 하려는 것이다.
  - **입력 흐름:** 모든 질문 페이지 맨 위에 Back 링크를 둔다. 브라우저 뒤로가기를 망가뜨리지 않는다.
  - **입력 흐름:** 힌트는 "마침표 없는 짧은 한 문장"이고 링크를 넣지 않는다.
  - **입력 흐름:** 필수 칸에 별표(*)를 쓰지 않는다. 선택 칸에는 "(optional)"을 붙인다. "I do not know"처럼 모른다는 답을 허용한다.
  - **입력 흐름:** 진행 표시는 먼저 없이 시험한다. 필요할 때만 "Question 3 of 9" 같은 캡션을 쓰고, 총수는 셀 수 있을 때만 적는다.
- 피할 것: 여러 질문을 한 화면에 묶는 것(사용자 조사 근거가 있을 때만 허용된다). 같은 제목을 여러 화면에 반복하는 것.

### 2. GOV.UK Design System: 답변 확인(Check answers) 패턴
- 주소: https://design-system.service.gov.uk/patterns/check-answers/
- 가져올 것:
  - **입력 흐름(확인):** 제목이 할 일을 말한다("Check your answers before sending your application"). 답은 'Personal details' 같은 소제목으로 묶고, 묶음마다 summary list(항목·값·Change 링크 3열)로 보여준다.
  - **입력 흐름(확인):** 각 Change 링크에는 화면 읽기용 숨은 글자로 무엇을 바꾸는지 붙인다(예: "name"). 바꾼 뒤에는 나머지 단계를 다시 거치지 않고 확인 페이지로 돌아온다.
  - **입력 흐름(확인):** 건너뛴 선택 질문은 "Not provided"로 보여준다. 긴 질문은 짧은 서술로 바꿔 항목명으로 쓴다.
  - **입력 흐름(확인):** 제출 버튼은 행동을 말한다(예: "Accept and send"). 버튼 위에는 확인해야 거래가 끝난다는 안내 문장을 둔다.
- 피할 것: 질문 문장을 그대로 길게 항목명으로 쓰는 것. '수정' 링크에 대상 정보를 빼먹는 것.
- 우리 적용(추정): '읽은 값 확인' 화면에서 OCR로 읽은 시급·기간 등을 이 목록으로 보여주고, 항목마다 '바꾸기'를 둔다.

### 3. GOV.UK Design System: 텍스트 입력·오류 요약·파일 업로드
- 주소:
  - https://design-system.service.gov.uk/components/text-input/
  - https://design-system.service.gov.uk/components/error-summary/
  - https://design-system.service.gov.uk/components/file-upload/
- 가져올 것:
  - **입력 흐름(숫자):** 정수에는 `inputmode="numeric"`, 소수에는 `inputmode="decimal"`을 쓴다. "Do not use `<input type="number">`"라고 명시돼 있다(조사로 필요가 확인될 때만 예외).
  - **입력 흐름(단위):** £, kg 같은 접두사·접미사는 입력칸 **밖**에 둔다. 화면 읽기가 읽지 않을 수 있으니 label이나 힌트에도 "Cost, in pounds"처럼 적는다. 사용자가 접두사를 직접 쳐도 오류를 내지 않는다.
  - **입력 흐름(폭):** 길이를 아는 값은 고정 폭 입력칸을 쓴다(우편번호·전화번호 등).
  - **입력 흐름(오류 문구):** 비어 있으면 "Enter [무엇]", 숫자가 아니면 "[무엇] must be a number", 범위 밖이면 "must be 16 or more"처럼 경계값을 말한다.
  - **입력 흐름(오류 요약):** `main` 맨 위, Back 링크 아래이자 h1 위에 "There is a problem" 제목으로 둔다. 요약 문장과 칸 옆 문장을 같게 쓰고, 요약 항목은 해당 칸으로 연결된다. 페이지 `<title>` 앞에 "Error:"를 붙인다.
  - **서류 업로드:** 서비스에 꼭 필요할 때만 업로드를 요청한다. 이미 올린 파일은 같은 흐름에서 다시 쓸 수 있게 한다. 다만 공용 기기에서는 미리보기를 조심한다.
  - **서류 업로드(오류):** 오류를 이유별로 나눈다. "Select a report", "The selected file must be smaller than 2MB", "The selected file is empty", "The selected file could not be uploaded – try again".
- 피할 것: `maxlength`로 글자를 몰래 자르는 것. 칸 옆 오류와 요약 오류의 문구가 다른 것.

### 4. VA.gov Design System (미국 보훈부)
- 주소:
  - https://design.va.gov/
  - https://design.va.gov/templates/forms/form-step
  - https://design.va.gov/patterns/help-users-to/check-answers
- 가져올 것:
  - **입력 흐름:** 버튼은 보조 "Back" 버튼과 주 "Continue" 버튼을 한 쌍으로 둔다. 마지막 단계에서는 "Continue"를 "Submit"으로 바꾼다.
  - **입력 흐름:** 'One thing per page'를 따른다. 질문이 하나뿐인 페이지는 제목과 label을 따로 둔다. 다만 라디오·체크박스 묶음은 제목이 label을 겸할 수 있다.
  - **입력 흐름:** 본문은 "fewer than 50 words"로 쓰고, 필수가 아닌 정보는 Details(접힘) 컴포넌트로 옮긴다.
  - **입력 흐름:** 분할 진행 막대를 쓰되 전체 13단계 이하를 권한다. 조건에 따라 경로가 갈리면 경로마다 별도 진행 막대를 만든다.
  - **확인 화면:** 흐름 끝에 두고, 단계 순서대로 아코디언으로 나눈다.
  - **쉬운 말:** 콘텐츠 원칙 목록이 있다. 어려운 말 풀어 쓰기, 관용구·전문용어 피하기, 능동태, 짧은 문장, 쉬운 단어.
- 피할 것: 확인 화면을 아코디언으로 모두 접어 두는 것(추정: 모바일에서 한눈에 확인하기 어렵다. 우리는 펼친 목록이 낫다).

### 5. U.S. Web Design System (USWDS)
- 주소:
  - https://designsystem.digital.gov/components/step-indicator/
  - https://designsystem.digital.gov/components/input-mask/
  - https://designsystem.digital.gov/components/language-selector/
- 가져올 것:
  - **입력 흐름(단계 표시):** "3개 이상의 큰 단계"가 있는 선형 과정에만 쓴다. 답에 따라 단계 수가 바뀌거나 섹션이 3개 미만이면 쓰지 않는다. 현재 단계에는 `aria-current="true"`를 붙인다.
  - **입력 흐름(입력 마스크):** 형식이 정해진 값에만 쓴다. 오류 표시는 사용자가 그 칸을 건드린 뒤에만 한다. 숫자에는 `inputmode="numeric"`을 쓴다.
  - **다국어:** 모든 페이지에 HTML `lang` 속성을 붙이고, 다른 언어로 가는 링크 글자에는 `<span lang="..">`을 붙인다. 두 언어면 2언어형을, 3개 이상이면 드롭다운형을 쓴다. 번역이 다 되지 않았으면 언어 선택기를 쓰지 않는다.
- 피할 것: 입력 마스크는 공개 시험에서 1건이 실패했다. "오류에서 회복하기 어렵다"는 알려진 문제가 있으니 금액 칸에 자동 쉼표 마스크를 강하게 걸지 않는다(추정).

### 6. GOV.UK 최저임금 계산기(근로자용) 시작 화면 + 시작 페이지 패턴 + Panel
- 주소:
  - https://www.gov.uk/am-i-getting-minimum-wage
  - https://design-system.service.gov.uk/patterns/start-using-a-service/
  - https://design-system.service.gov.uk/components/panel/
- 가져올 것:
  - **입력 흐름(시작):** 제목은 "National Minimum Wage and Living Wage calculator for workers"이다. "Check if:" 아래에 확인할 수 있는 3가지를 나열한다. 그중 하나가 "your employer owes you past payments ... because of underpayment"로, 우리 서비스와 같은 목적이다. 시작 버튼은 "Start now"이다.
  - **입력 흐름(시작):** 시작 페이지에는 서비스가 하는 일, 걸리는 시간, 준비물(서류) 목록, 다른 이용 방법(전화 등)을 넣는다. 복잡한 자격 조건은 시작 페이지가 아닌 서비스 안 질문으로 묻는다. 주 행동은 링크가 아닌 버튼이다.
  - **결과 화면:** Panel은 확인(완료) 페이지와 중단 페이지에서만 쓰고 "Never use the Panel component to highlight any other information"이라고 못박는다. 패널 문장은 모바일 확대에서도 읽히게 짧게 쓴다.
- 피할 것: 결과 강조 상자를 결과 화면 밖 여기저기(안내·팁 등)에 쓰는 것. 이 계산기 화면에는 언어 전환이 없다(웨일스어 서비스 목록 링크만 있다). 이 점은 우리가 따라 하면 안 된다.

### 7. 고용노동부 최저임금 모의계산
- 주소: https://www.moel.go.kr/miniWageMain.do (메인 https://www.moel.go.kr/ 은 본문이 불러와지지 않아 직접 확인 못 함)
- 가져올 것:
  - **입력 흐름:** 입력은 6개 묶음(근로시간, 기본급, 상여금·수당, 복리후생비, 기타수당, 수습 여부)이고 순서대로 받는다. 각 묶음에는 "2024년부터 매월 지급하는 상여금은 최저임금에 전부 포함됩니다" 같은 법 근거 설명이 붙어 있다. 우리 '질문 6단계'의 항목 구성을 맞춰 볼 기준이 된다.
  - **결과 화면:** 결과는 '위반 소지 있음 / 없음' 두 가지 메시지다. 둘 다 "임금 구조가 복잡하면 정확하지 않을 수 있다"는 단서가 붙고, 문의는 지방노동관서로 안내한다. 47개 지방관서 전화번호 목록이 있다(첫 줄 서울청 02-2213-0009).
- 피할 것:
  - 한 화면에 6개 묶음을 모두 늘어놓는 것. '장려가급', '실비변상', '주휴일' 같은 법률 용어를 그대로 label로 쓰는 것. 우리는 쉬운 말로 바꾸고 원래 용어는 괄호나 '자세히'에 둔다.
  - 결과를 위반 여부만 말하고 금액을 주인공으로 두지 않는 것.

### 8. 호주 Fair Work Ombudsman: Pay and Conditions Tool (PACT)
- 주소: https://calculate.fairwork.gov.au/findyouraward (첫 화면만 확인. 이후 질문 화면과 언어 도움 페이지 https://www.fairwork.gov.au/language-help 는 시간 초과로 직접 확인 못 함)
- 가져올 것:
  - **입력 흐름:** 첫 질문은 사용자 구분이다. "I'm an employee looking for pay rates" / "I'm an employer or business looking for pay rates" 중 하나를 고르고, 이어서 "Show me pay rates as at"으로 날짜를 받는다.
  - **입력 흐름:** "Save", "Start again", "Saved sessions" 기능이 있다. 중간에 저장하고 나중에 이어 할 수 있다.
  - **다국어:** 머리말과 옆 메뉴 두 곳에 통역사 아이콘과 함께 "Language help" 링크가 있다.

### 21. GOV.UK A to Z 문체 가이드 (숫자·금액 표기)

## 'AI가 만든 티'를 피하기 위해 이 조사에서 얻은 근거

- 위 공공 디자인 시스템(GOV.UK, VA, USWDS, Canada.ca)의 확인한 페이지 어디에도 그라디언트·이모지 아이콘·둥근 카드 나열을 권하는 내용은 없었다. 반대로 다음을 권했다.
  - 왼쪽 정렬 버튼과 왼쪽 정렬 제목 (1)
  - 강조 상자는 결과·중단 화면에서만 쓰기 (6)
  - 색과 장식은 결과·제목 강조에만 쓰기 (13)
- GOV.UK의 포커스 노랑 `#ffdd00` + 먹색 `#0b0c0c` 조합은 우리 '노랑 포인트 + 먹색 글씨' 방향과 같다. 노랑은 장식이 아닌 '지금 여기'를 알리는 기능색으로 쓴다. (9)

## 4단계 앱 느낌 (휴대폰을 '설치한 앱'처럼)

4단계 담당이 중간에 끊겨 5단계에서 이어서 정리했다. 원리만 가져오고 화면은 베끼지 않았다. 근거는 아래 '5단계' 조사 파일.

| 원리 | 출처에서 확인한 것 | 우리 화면에 적용한 것 |
|---|---|---|
| 아래 탭 막대는 3~5개, 한 단어 라벨, 이동 전용 | Material 3 내비게이션 바, Apple HIG 탭 막대, Monzo(탭 3→5개) | 결과 뒤에만 4개 탭(결과 · 절차 · 노동청 · 준비물). 입력 흐름 중에는 숨김(모달 흐름으로 봄) |
| 시트는 간단한 일 하나, 손잡이 · 바깥 누르기 · 아래로 쓸기로 닫힘 | Apple HIG 시트, Material(M1) 바텀시트, 토스 TDS BottomSheet | 확인 · 쉬운 말 풀이 · 언어 · 항목 상세 · 내 정보 지우기를 아래 시트로. 아래 버튼은 1~2개 |
| 목록 줄: 왼쪽 아이콘 · 글 · 오른쪽 꺾쇠, 누르면 바로 반응 | 토스 TDS ListRow | 밑줄 웹 링크를 목록 줄(`.nav-row`)로. 누를 때 살짝 작아짐 + 배경색 |
| 불러오는 중에는 실제 배치 모양의 뼈대 | 토스 TDS Skeleton | 쉬운 설명 · 노동청 목록을 읽는 동안 뼈대(`.skel`) |
| 첫 화면은 가장 먼저 할 일, 버튼 글은 일어날 일 | 토스 앱인토스 UX 원칙 | 시작 화면은 제목 2줄 · 한 줄 설명 · 언어 · 동의 · 버튼 2개만 |
| 큰 금액만 크게, 색 강조는 결과 하나 | 토스 앱인토스 UX 원칙 | 결과 화면 맨 위 합계 카드 하나만 진하게, 항목은 한 줄 목록 |
| 안전 영역 안에 조작부, 배경은 끝까지 | Apple HIG 레이아웃 | 아래 고정 영역 · 시트에 `env(safe-area-inset-bottom)` |
| 언어 바꾸기는 모든 화면 위 오른쪽 같은 자리, 바꿔도 입력 유지 | DWP 웨일스어 전환 패턴 | 앱바 오른쪽 언어 단추 → 시트. 입력값은 그대로 |

화면 전환(옆으로 밀기) 규칙은 다섯 금융 앱 공개 문서 어디에서도 찾지 못했다. 그래서 모바일 운영체제의 일반적인 쌓기(stack) 이동 동작을 따랐고, '움직임 줄이기' 설정이면 끈다.
